# 📄 제품 요구사항 정의서 (Product Requirements Document - PRD)

**프로젝트명:** 사원정보 기반 싱글 사인온(SSO) 통합 인증 관리 애플리케이션 (Lightkey SSO System)
**문서 상태:** 구현 완료 후 향후 고도화 반영(v1.1.0 준비)

---

## 1. 프로젝트 개요 및 목표

### 1.1 개요
Lightkey SSO 시스템은 한 번의 인증(Single Sign-On)으로 기업 내 다양한 사내 시스템 및 그룹웨어(Service Provider)에 안전하고 편리하게 접근할 수 있는 중앙 집중형 인증 시스템(Identity Provider, IdP)입니다.

### 1.2 목표 (현 단계 달성 사항)
오픈 소스 프레임워크인 NestJS 및 Next.js를 바탕으로 OAuth 2.0 (Authorization Code Grant) 인프라를 독자 구축하고, 인사 시스템 데이터 동기화를 통해 전사 직원의 단일 로그인 경험을 제공하며, 시스템 관리자의 강력한 중앙 통제권(접근 차단, 세션 파기 등)을 보장합니다.

---

## 2. 사용자 역할 (Roles)

1.  **일반 사원 (ROLE_USER):** 식별 가능한 사번과 비밀번호로 통합 페이지에 로그인하여, 등록된 사내 앱들에 별도 인증 없이 접근하는 권한을 가집니다. 로그인 5회 실패 시 계정이 잠금 처리됩니다.
2.  **시스템 관리자 (ROLE_ADMIN):** 인증 세션을 모니터링하고, 잠긴 사용자의 계정을 복구(Unlock)하며, 사내 파트너 앱(SP)을 등록하고 허용 IP(Allowlist)를 통제하는 최상위 운영 권한을 갖습니다.

---

## 3. 핵심 기능 요구사항 (Functional Requirements)

### 3.1 통합 인증 파트 (Authentication & SSO)
*   **FR-1. 중앙 집중식 통합 로그인:** 사번 필드를 식별자로 하여 유일한 인증 페이지 창구(`/login`)를 제공해야 합니다.
*   **FR-2. 보안 세션 쿠키 발급:** 브라우저 탈취(XSS)를 원천 봉쇄하기 위하여 토큰은 반드시 `HttpOnly`, `Secure` 옵션을 적용한 쿠키 형태로 발급 및 저장해야 합니다.
*   **FR-3. OIDC/OAuth 2.0 인가 코드 흐름:** 연동 앱 접근 시 사용자 인증 후 1회성 인가 코드(Code)를 발급하고, SP 백엔드와의 M2M 통신을 거쳐 Access Token을 교환해 주는 스펙을 준수해야 합니다.
*   **FR-4. 통합 로그아웃 (SLO):** SSO 허브 단에서의 로그아웃이 Redis 세션을 즉각 파기하여 연동 서비스로 파급되는 중앙 통제 로그아웃 뼈대를 가져야 합니다.

### 3.2 계정 관리 및 전사 동기화 (Account & Sync)
*   **FR-5. 단일 데이터 출처 (SSOT):** 회원가입 기능은 배제하고, 배치 태스크를 통해 자체 인사 데이터(CSV 형식)를 일정 주기로 파싱하여 DB 레코드를 동기화(Upsert)해야 합니다.
*   **FR-6. 예외적 수동 계정 생성:** 부득이한 경우(외부 파트너, 감사업체 등)를 대비해 관리자가 강제로 계정(`employeeId`, 임시 비밀번호)을 생성하는 관리자 API를 갖춰야 합니다.
*   **FR-7. 계정 보안 잠금:** 무차별 암호 대입(Brute-force)을 막기 위해 5회 이상 로그인 연속 실패 시 계정을 잠가야(`isLocked=true`) 합니다.

### 3.3 어드민 통합 관제 (Admin Control)
*   **FR-8. 사용자 액세스 모니터링:** 시스템 내 활성자 및 비활성자, 가장 최근 로그인 시간(Last Login)을 목록 형태로 조회해야 합니다.
*   **FR-9. SP(Service Provider) 생애주기 관리:** OAuth 인증을 받고자 하는 엔드포인트에 대한 등록/수정/삭제 기능을 지원해야 하며, 생성 시점에만 `Client Secret`을 평문 노출하고 이후는 복호화 불가능한 단방향 해시로 저장해야 합니다.
*   **FR-10. IP 허용 대역 (Allowlist) 제어:** 특정 SP마다 인가 코드를 토큰으로 맞바꿀 수 있는 IP(혹은 CIDR) 망 대역을 제한하여 방화벽 수준의 M2M 보안 통제를 보장해야 합니다.

## 4. 향후 고도화 목표 (Next Steps from Agent Reviews)

본 시스템은 현재 MVP로서 기능이 완비되었으나, 상용 오픈(v1.1)이나 트래픽 확장을 위해 다음의 개선 사항 달성을 향후 스프린트 요구사항으로 정의합니다.

### 4.1 성능 및 아키텍처 개선 (Backend & DBA)
*   **NR-1. 대규모 트래픽 대비 파티셔닝:** `login_histories` 등 로그성 테이블의 급격한 팽창에 대비해 DB Table Partitioning을 적용한다.
*   **NR-2. Redis 고가용성 보장:** 단일 장애점(SPOF) 회피를 위해 세션 DB인 Redis를 Cluster 혹은 Sentinel 구조로 이중화 구성을 꾀한다.

### 4.2 사용자 경험 (UX) 고도화 (Frontend)
*   **NR-3. 대용량 Data Grid 처리:** 수만 명 단위의 사원 목록, 수백 개의 SP 목록을 어드민 대시보드에 렌더링하기 위해 Backend의 페이징(Pagination) API를 연결하고 검색(Search) 기능을 구현한다.
*   **NR-4. 친절한 예외 상황 UI 제공:** 백엔드에서 뱉는 401(Unauthorized), 403(Forbidden, IP Block) 에러를 프론트엔드에서 캐치하여 사용자 친화적인 안내 화면으로 포워딩한다.

### 4.3 품질 및 배포 파이프라인 (DevOps & QA)
*   **NR-5. 자동화 E2E / 통합 테스트:** Playwright 등을 이용해 "로그인 -> SSO Code 교환 -> 토큰 획득" 인증 주기가 코드 배포 시마다 자동 검증(Regression 방지)되게 한다.
*   **NR-6. CI/CD 파이프라인 셋업:** 머지 리퀘스트(MR/PR) 시 Lint 및 Build 패스 여부를 강제하는 자동화 액션을 구축한다.
